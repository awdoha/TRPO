## 1. Платформа .NET: IL, JIT, Assembly ◽

**Простыми словами.** Пишешь C# → компилятор делает **IL** (промежуточный код, не привязанный к процессору) → при запуске **JIT** переводит нужные методы в **машинный код** → процессор выполняет. Результат компиляции проекта — **сборка** (`.exe` или `.dll`) — внутри IL, метаданные (какие есть типы), ресурсы, манифест (имя, версия, зависимости).

**Как ответить.** «C# не превращается сразу в машинный код: цепочка C# → IL → JIT → машинный код. Благодаря IL разные языки (C#, F#, VB) работают на одной платформе, а JIT подстраивается под конкретный процессор. Сборка — это .exe/.dll, где лежат IL, метаданные, ресурсы и манифест».

**Где в моих работах.**
- Любой `.csproj`: [3пр] `Lab3\Lab3.csproj:4,5` (`net10.0-windows`, `WinExe`), [5пр] `Lab5\Lab5.csproj`, [6пр] `Lab6\Lab6.csproj` (`net10.0`).

## 2. Ссылочные и значимые типы ⭐

**Простыми словами.** **Значимые** (`int`, `double`, `bool`, `char`, `struct`, `enum`, `DateTime`) — переменная хранит **само значение**; при присваивании копируется значение. **Ссылочные** (`class`, `string`, массивы, `interface`, `delegate`, `record`) — переменная хранит **адрес** объекта; при присваивании копируется адрес, два имени → один объект.

```csharp
int a = 10; int b = a; b = 20;         // a == 10 (копия)
var p1 = new Person{Name="Anna"}; var p2 = p1;
p2.Name = "Maria";                      // p1.Name == "Maria" (одна ссылка)
```

**Как ответить.** «Значимый тип копирует данные, ссылочный копирует адрес. Значимые обычно в стеке/внутри объекта, ссылочные — в управляемой куче под контролем GC».

**Дополнительно (спрашивали: «для чего тип record»).** `record` — **ссылочный** тип (по умолчанию `record class`) для **данных**: автоматически даёт равенство **по значению** (два record с одинаковыми полями равны, `==` сравнивает содержимое), красивый `ToString()`, `GetHashCode`, деконструкцию и `with` (копия с изменением: `p with { Name = "X" }`). Позиционный record `record P(int Id, string Name)` создаёт неизменяемые свойства и конструктор. Есть ещё `record struct` (значимый).

**Где в моих работах.**

## 3. Nullable-типы: `?`, `!`, `??` ⭐

**Простыми словами.** `int?` = «число или null» (`Nullable<int>`, значимый тип, который может быть «пусто»). `string?` = «строка может быть null» (подсказка компилятору, C# 8+). Операторы:
- `?.` — безопасный доступ: `person?.Name` (если `person == null`, вернёт null, без исключения);
- `??` — значение по умолчанию: `age ?? 0`; `??=` — присвоить, если null;
- `!` — «я уверен, что не null» (просто убирает предупреждение; **от NullReferenceException не защищает**).

**Как ответить.** «Nullable нужен, чтобы явно показать, что значения может не быть. `?.` безопасно обращается, `??` подставляет значение по умолчанию, `!` только заглушает компилятор и требует осторожности».

**Где в моих работах.** Везде `<Nullable>enable</Nullable>` в `.csproj`.

## 4. Свойства ⭐

**Простыми словами.** Свойство выглядит как поле, но внутри — методы `get`/`set`: можно проверять значение, вычислять, ограничивать доступ. Поле — просто переменная класса; свойство — контролируемый доступ к нему.

Виды:
```csharp
private int age;                                // полная форма
public int Age { get { return age; } set { if (value >= 0) age = value; } }
public string Name { get; set; }                // авто-свойство (скрытое поле создаёт компилятор)
public int Id { get; }                          // только чтение (задать можно в конструкторе)
public int Id2 { get; private set; }            // читать снаружи можно, менять — только внутри
public string Full => First + " " + Last;       // вычисляемое
```
`value` в `set` — то, что стоит справа от `=`. Свойство отвечает «какое значение?», метод — «что сделать?».

## 5. Полиморфизм 🔥

**Простыми словами.** Работаешь с объектами разных классов через **общий тип** (базовый класс или интерфейс), а поведение определяется **реальным** объектом. `List<Figure>` из `Circle` и `Rectangle`: вызов `figure.Draw()` каждый выполнит по-своему.

Механика: в базовом классе метод `virtual`, в наследнике — `override`.
```csharp
class Figure   { public virtual void Draw() => Console.WriteLine("фигура"); }
class Circle : Figure { public override void Draw() => Console.WriteLine("круг"); }
Figure f = new Circle(); f.Draw();   // "круг"  (смотрит на реальный объект)
```

**⚠ Ловушка из переписки: «в чём разница, если пишем `override` и если пишем без `override`?»**
- С `override` (при `virtual`/`abstract` в базе) — **переопределение**: вызов через переменную базового типа исполнит версию наследника (позднее связывание, во время выполнения).
- **Без `override`** (просто такой же метод в наследнике) — это **скрытие** (как `new`): компилятор предупредит (CS0114). Вызов через переменную **базового** типа выполнит **базовый** метод; только через переменную типа наследника — новый. Полиморфизма нет.
- Если метод в базе **не** `virtual`/`abstract`, `override` написать нельзя.
- **Переопределение (override)** — в наследнике, работает во время выполнения. **Перегрузка (overload)** — в одном классе методы с одним именем, но разными параметрами, выбирается при компиляции.
- Полиморфизм бывает и через **интерфейсы** (`List<IDrawable>`).

## 6. Интерфейсы 🔥

**Простыми словами.** Интерфейс — **контракт**: список членов (методы, свойства, события), которые класс **обязан** реализовать. Класс наследует один класс, но реализует **много** интерфейсов. Зачем: меньше связей с конкретными классами, легче подменять реализации и тестировать, полиморфизм.

- **Неявная реализация** — обычные `public`-члены: `public void Move() {...}` (вызывается и через класс, и через интерфейс).
- **Явная реализация** — `void IMovable.Move() {...}`: без модификатора доступа, виден **только** через переменную типа интерфейса. Нужна при конфликте имён (два интерфейса с одним методом) или чтобы скрыть член.

```csharp
interface IMovable { void Move(); }
class Car : IMovable { public void Move() => Console.WriteLine("едет"); }
IMovable m = new Car(); m.Move();
```

## 7. Делегаты: Action / Func / Predicate ⭐

**Простыми словами.** Делегат — **тип «ссылка на метод»** с определённой сигнатурой (параметры + результат). Метод можно положить в переменную и вызвать через неё; передать как параметр.
```csharp
delegate int Operation(int a, int b);
static int Sum(int a, int b) => a + b;
Operation op = Sum; op(2,3);              // 5
static int Calc(int a, int b, Operation f) => f(a, b);   // поведение как параметр
```
**Многоадресный** делегат хранит несколько методов (`+=`), вызывает по очереди — на этом построены **события**.

Встроенные:
- `Action` / `Action<T>` — метод **без результата** (`void`): `Action<string> print = s => Console.WriteLine(s);`
- `Func<..., TResult>` — метод **с результатом**, **последний** тип — результат: `Func<int,int,int> add = (a,b) => a+b;`
- `Predicate<T>` — проверка условия, возвращает `bool`: `Predicate<int> even = x => x % 2 == 0;`

**Простыми словами.** **Анонимный метод** — метод без имени (`delegate(string s) { ... }`). **Лямбда** — короче: `параметры => выражение` (или `=> { блок }`). Используется с делегатами, событиями, LINQ. Лямбда может **захватывать** переменные окружения.

## 9. LINQ: общие принципы, формы запросов ◽

**Простыми словами.** LINQ = запросы к данным прямо в C# (коллекции, XML, БД через EF). Описываешь **что** получить, а не **как** перебирать. Две формы:
```csharp
var even1 = numbers.Where(x => x % 2 == 0);                  // методная (чаще всего)
var even2 = from n in numbers where n % 2 == 0 select n;      // запросная (как SQL)
```
Методная — цепочки методов расширения `System.Linq` (`Where`, `Select`, `OrderBy`, `GroupBy`, `First`, `Any`, `Count` …) + лямбды. Запросная удобна при нескольких источниках/группировках/join.

## 11. Отложенное выполнение LINQ, захват переменных 🔥

**Простыми словами.** Запрос с `Where/Select/OrderBy/GroupBy/Take/Skip` **не выполняется в момент объявления** — он только «запоминает рецепт». Реально считается при **переборе** (`foreach`) или при вызове «немедленных» методов (`ToList`, `ToArray`, `Count`, `First`, `Single`, `Max/Min/Sum/Average`, `ToDictionary`).
```csharp
var list = new List<int>{1,2,3};
var q = list.Where(x => x > 1);   // ещё ничего не считали
list.Add(4);
foreach (var n in q) ...          // выведет 2, 3, 4 — 4 попал, т.к. запрос выполнился позже
var snap = list.Where(x => x > 1).ToList();   // «снимок» — дальше не меняется
```
**Захват внешних переменных:** лямбда берёт значение переменной **в момент выполнения**, а не создания:
```csharp
int limit = 3; var q = list.Where(x => x > limit);
limit = 1; foreach (var n in q) ... // фильтр уже "больше 1"
```
Чтобы зафиксировать — `ToList()` сразу.

**Как ответить.** «Отложенное выполнение — запрос выполняется при переборе, а не при объявлении; результат зависит от состояния данных в момент выполнения. Методы, которым нужен результат сразу (`ToList`, `Count`, `First`), выполняют запрос немедленно».

**Где в моих работах.**
- [4пр] `LinqSolver.cs:44-47` — запрос `words` только описан, выполняется в `:53` (`ToList()`); `:66` `ToList()` — материализация словарей; `First/Max/Sum/All` — немедленные.

## 15. Сборщик мусора (GC) 🔥

**Простыми словами.** GC автоматически освобождает память **управляемых** объектов, до которых **нельзя добраться** от «корней» (локальные переменные активных методов, статические поля, ссылки из потоков, живые объекты). `person = null` — не удаляет сразу, только делает кандидатом.

**Поколения:** Gen 0 — новые короткоживущие (собирается чаще всего, быстро); Gen 1 — пережившие одну сборку (буфер); Gen 2 — долгоживущие (кэш, статика; собирается редко, дорого). Идея: большинство объектов умирает молодыми, поэтому молодых проверяют чаще. Есть ещё LOH (большие объекты).

**Вызов вручную:** `GC.Collect(); GC.WaitForPendingFinalizers();` — в обычном коде **не рекомендуется**.

**Как ответить.** «GC — автоматическое управление памятью. Он ищет недостижимые объекты, использует три поколения для скорости, и вручную его обычно не вызывают. Неуправляемые ресурсы GC не освобождает — для них `IDisposable`/`using`».

**Где в моих работах.** Явных вызовов `GC` нет (это нормально). Косвенно: все `new`-объекты (`List`, `Shape`, `CellViewModel`, `GameField`) собирает GC — [5пр] при импорте JSON старые `GameField` и клетки (`Cells.Clear()`) становятся мусором; [3пр] точки/фигуры после `Очистить` (`ClearAll`); а вот **GDI-объекты `Pen`/`Brush` освобождаем вручную** через `using var` — `MainForm.cs:205,216` — это связка GC + Dispose (вопрос 16).

## 16. Неуправляемые ресурсы, финализаторы, `using`, Dispose 🔥

**Простыми словами.** **Управляемая** память (объекты, строки, списки) — забота GC. **Неуправляемые ресурсы** — файлы, сокеты, соединения с БД, GDI-дескрипторы, окна, указатели: GC их сам не закроет вовремя. Для этого класс реализует `IDisposable` с методом `Dispose()`.

- **`using`** гарантирует вызов `Dispose()` даже при исключении:
  ```csharp
  using (var r = new StreamReader("a.txt")) { ... }   // классический
  using var r2 = new StreamReader("a.txt");           // современный — до конца области видимости
  ```
  Компилятор раскрывает это в `try { ... } finally { r.Dispose(); }`.
- **Что происходит в `Dispose`** (спрашивали): закрываются/освобождаются ресурсы (файл, соединение, GDI-объект), обнуляются ссылки, при наличии финализатора вызывается `GC.SuppressFinalize(this)`, чтобы GC не вызывал его повторно. Часто реализуют «паттерн Dispose» (`Dispose(bool disposing)`).
- **Финализатор** `~MyClass()` — вызывается GC **перед удалением** объекта, **когда — неизвестно**. Это запасной вариант, если забыли `Dispose`. Минусы: непредсказуем, замедляет сборку (объект живёт ещё одну сборку).
- **Dispose vs финализатор:** `Dispose` — явно и сразу; финализатор — позже, неопределённо. Правильно: `Dispose` + `using`, финализатор — страховка.

**Где в моих работах.**
- [3пр] `using var pointBrush = new SolidBrush(...)` — `MainForm.cs:205`; `using var pen` — `:216`; `using (var fillBrush = ...)` — `:236`; `using var form = new ParametersForm(...)` — `:154` (модальное окно освобождается при выходе из метода).
- [4пр] `using var axisPen = new Pen(...)` — `MainForm.cs:405,409,509`; `Dispose` формы — `MainForm.Designer.cs:13-20`; тесты `SolversTests : IDisposable` (`SolversTests.cs:8,18` — удаление временных файлов).

## 17. Указатели, `fixed` ⭐

**Простыми словами.** Указатели в C# — только в `unsafe`-коде (нужен флаг проекта `AllowUnsafeBlocks`). `&x` — адрес, `*p` — значение по адресу. GC может **перемещать** объекты в памяти (уплотнение кучи), поэтому, чтобы взять стабильный адрес управляемого объекта (массива), используют **`fixed`** — он временно «закрепляет» объект.
```csharp
unsafe {
    int n = 10; int* p = &n; Console.WriteLine(*p);
    int[] a = {1,2,3};
    fixed (int* q = a) { Console.WriteLine(q[0]); }   // на время блока массив не двигается
}
```
**Как ответить.** «Указатели в C# нужны редко — интероп, высокая производительность; работают только в unsafe. `fixed` закрепляет объект, чтобы GC не переместил его, пока мы работаем с адресом».

**Где в моих работах.** **Нет** (`unsafe` не используется) — так и скажи: «в работах не применялось; в WinForms/WPF/EF всё идёт через управляемые ссылки, дескрипторами GDI занимается `System.Drawing`».

## 18. Асинхронность 🔥

**Простыми словами.** Долгие операции (файл, сеть, БД, задержка) не должны блокировать поток — особенно **UI-поток**, иначе окно «зависнет». `Task` — «обещание» результата (как **Promise** в JS): `Task` — операция без результата, `Task<T>` — вернёт `T`.
- `async` — метод **разрешает** использовать `await`; он **не создаёт новый поток**.
- `await` — «дождись завершения, но не блокируй поток»; после завершения метод продолжается со следующей строки. Пока ждём, поток свободен.
```csharp
private async void Button_Click(object s, EventArgs e)   // async void — только для обработчиков событий
{
    var text = await File.ReadAllTextAsync("a.txt");     // UI не зависает
}
async Task<int> GetNumberAsync() { await Task.Delay(1000); return 10; }
```
- `Task.Run(() => ...)` — выполнить тяжёлую синхронную работу в потоке пула.
- **Контекст синхронизации (SynchronizationContext):** в WinForms/WPF после `await` выполнение **возвращается в UI-поток** (поэтому можно трогать контролы). В ASP.NET Core такого контекста нет. `ConfigureAwait(false)` = «продолжай где угодно».

**Ловушки из переписки.**
- **«Любой ли метод может быть async?»** — нет. Нельзя у **конструктора, финализатора, свойства** (`get/set`), метода с `ref/out/in`-параметрами. Допустимые типы результата: `Task`, `Task<T>`, `ValueTask(<T>)`, `void` (только обработчики событий), `IAsyncEnumerable<T>`. `async` без `await` внутри — предупреждение, метод выполнится синхронно.
- **Почему `async void` плох:** его нельзя `await`-ить, исключения сложно перехватить; допустим лишь у обработчиков событий (сигнатура возвращает `void`).
- **Task vs Promise:** идея та же; но в C# `await` возвращает в исходный контекст, есть `Task.WhenAll/WhenAny`, отмена через `CancellationToken`.

**Где в моих работах.**
- **[4пр] единственное реальное использование:** `private async void OnRunClick(...)` — `Lab4.UI\MainForm.cs:88` (обработчик кнопки → `async void` допустим); `async Task ...` — `:158,185,213,237`; `await Task.Run(() => solver.GetPopularCharPair(files))` — `:160,187,215,239` — тяжёлый расчёт уходит в пул, UI не зависает.

## 22. Привязка данных в WPF: DataContext, Resources ◽

**Простыми словами.** `Binding` связывает свойство элемента со свойством объекта: `<TextBox Text="{Binding UserName}"/>`. Источник по умолчанию — **`DataContext`**; он **наследуется вниз по дереву** (сначала берётся у элемента, потом у родителя, выше…), можно переопределить локально (`<Grid DataContext="{Binding SelectedUser}">`). Другие источники: `ElementName`, `Source`, `RelativeSource`.

- `INotifyPropertyChanged` — чтобы UI узнал об изменении свойства во ViewModel.
- **Resources:** хранят стили, шаблоны, кисти. Поиск ресурса — от элемента вверх → `Window.Resources` → `App.xaml`. `StaticResource` — один раз при загрузке; `DynamicResource` — обновляется на лету (темы).
- **Триггеры:** `Trigger` (по свойству элемента) и `DataTrigger` (по значению из привязки).

## 24. Загрузка связанных данных в EF Core ⭐ (спрашивали: «три способа, с конкретным примером»)

**Проблема.** Получил `Notes`, а `Categories` у них **пусты**, пока явно не загрузил.

**Способ 1 — Eager (жадная): `Include` / `ThenInclude`** — связанное грузится **сразу**, одним запросом.
```csharp
var notes = context.Notes.Include(n => n.Categories).ToList();
var bands = context.Bands.Include(b => b.Albums).ThenInclude(a => a.Genre).ToList();  // вложенные связи
```
**Способ 2 — Explicit (явная):** сущность уже загружена, связь дозагружаем **отдельно и по требованию**.
```csharp
var note = context.Notes.First();
context.Entry(note).Collection(n => n.Categories).Load();   // коллекция
context.Entry(album).Reference(a => a.Band).Load();          // одиночная ссылка
```
**Способ 3 — Lazy (ленивая):** грузится **автоматически при обращении** к навигационному свойству. Нужны пакет `Microsoft.EntityFrameworkCore.Proxies`, `UseLazyLoadingProxies()` и `virtual` навигационные свойства. Минус: «проблема N+1» — на каждый элемент цикла отдельный запрос.
```csharp
var note = context.Notes.First();
Console.WriteLine(note.Categories.Count);   // тут EF сам сделает запрос
```

**Как выбрать.** Eager — когда точно нужно; Explicit — когда нужно не всегда; Lazy — удобно, но опасно для производительности.

**Где в моих работах — [6пр].** Использован **eager**: `.Include(n => n.Categories)` — `Data\EFNoteRepository.cs:18`; `.Include(c => c.Notes)` — `:76` (обратная сторона). Explicit/Lazy в проекте не применены — можно показать пример выше на `Note`/`Category`.

## 28. Принципы SOLID 🔥🔥 (самый частый вопрос: спрашивали D ×3, L ×2, S, O)

| Буква | Принцип | Смысл в одну фразу | Признак нарушения |
|---|---|---|---|
| **S** | Single Responsibility | у класса **одна причина для изменения** | «божественный класс», делает всё |
| **O** | Open/Closed | **открыт для расширения, закрыт для изменения**: новое поведение — новым классом | длинные `if/switch` по типу — при новом типе правишь старый код |
| **L** | Liskov Substitution | **наследник должен подставляться вместо базового** без поломки | `Penguin : Bird` с `Fly()`, бросающим исключение |
| **I** | Interface Segregation | **лучше несколько узких интерфейсов**, чем один широкий | пустые методы-заглушки, `NotImplementedException` |
| **D** | Dependency Inversion | **зависеть от абстракций, а не от конкретных классов**; реализацию передают снаружи (DI) | `new EmailSender()` прямо в `OrderService` |

**Мини-пример D:**
```csharp
interface IMessageSender { void Send(string m); }
class OrderService {
    private readonly IMessageSender _s;
    public OrderService(IMessageSender s) { _s = s; }   // получает снаружи
}
```

## 29. Контейнеры управления зависимостями (DI) ⭐

**Простыми словами.** **DI (Dependency Injection)** — класс не создаёт зависимости через `new`, а **получает их извне**, чаще через конструктор. **DI-контейнер** знает: какой интерфейс какой реализацией заменить, когда создавать объект, сколько он живёт, какие зависимости нужны ему самому — и **сам собирает цепочку** (контроллер → репозиторий → DbContext). Реализует принцип **D** из SOLID; облегчает тесты (подсунуть заглушку).

Регистрация в `Program.cs`:
```csharp
builder.Services.AddTransient<IMessageSender, EmailSender>();   // новый объект при каждом запросе
builder.Services.AddScoped<OrderService>();                     // один на HTTP-запрос
builder.Services.AddSingleton<AppCache>();                      // один на всё приложение
```
**Времена жизни:** **Transient** — каждый раз новый (лёгкие сервисы без состояния); **Scoped** — один на область (в вебе — один HTTP-запрос): `DbContext`, репозитории; **Singleton** — один на всё приложение (кэш, конфигурация; осторожно с потокобезопасностью; Singleton не должен зависеть от Scoped).

**Где в моих работах — [6пр] (это главный пример).**
- `AddControllersWithViews()` — `Program.cs:8`; `AddDbContext<NoteContext>(...)` — `:16` (по умолчанию **Scoped**); `AddScoped<INoteRepository, EFNoteRepository>()` — `:17`.
- Внедрение через конструкторы: `NoteController.cs:12` (получает `INoteRepository`), `EFNoteRepository.cs:11` (получает `NoteContext`), `NoteContext` (получает `DbContextOptions`) — контейнер строит цепочку сам.
- [5пр], [3пр] — контейнера нет: зависимости создаются вручную (`MainViewModel.cs:23`; `new ParametersForm(...)` — `MainForm.cs:154`).
